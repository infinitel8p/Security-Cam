# Starting Security-Cam

Now that you have completed the setup ([hardware](../setup/hardware), [WiFi AP](../setup/wifi), [Bluetooth](../setup/bluetooth), [MediaMTX](../setup/mediamtx)), you can start the Security-Cam system.

## Quick start

To start both the Flask backend and Astro frontend manually:

```bash
cd /opt/security-cam
./start.sh
```

This launches:
- **Flask API** on port `5005` - handles recording, system monitoring, device detection
- **Astro frontend** on port `3000` - the web dashboard (serves pre-built static files)

:::note
The frontend must be built before the first start. This is done automatically by `install_requirements.sh`. If you change frontend code, rebuild with:

```bash
cd /opt/security-cam/server && npm run build
```
:::

Open the dashboard in your browser:

```
http://<raspberry-pi-ip>:3000
```

If you're connected to the Pi's Access Point:

```
http://192.168.4.1:3000
```

## Running as a systemd service

The recommended way to run Security-Cam is as a systemd service. On every boot it will automatically pull the latest code from git, rebuild if anything changed, and start the servers.

### Install the service

```bash
sudo cp /opt/security-cam/client/data/security-cam.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable security-cam.service
sudo systemctl start security-cam.service
```

### Check the status

```bash
sudo systemctl status security-cam.service
```

### How auto-update works

The service runs `setup/update.sh` before starting. This script:

1. Runs `git pull` to fetch the latest code
2. Compares the current commit with the last successful build
3. If the code changed, runs `install_requirements.sh` (installs deps + rebuilds frontend)
4. Saves a stamp so it skips the rebuild on next boot if nothing changed

To force a rebuild (e.g. after manually editing files):

```bash
sudo /opt/security-cam/setup/update.sh --force
sudo systemctl restart security-cam
```

## Verifying everything is running

After a fresh boot, all services should be active:

```bash
sudo systemctl status hostapd --no-pager
sudo systemctl status mediamtx --no-pager
sudo systemctl status security-cam --no-pager
```

| Service | Purpose | Port |
| --- | --- | --- |
| `hostapd` | WiFi Access Point | - |
| `mediamtx` | Camera stream (WebRTC/RTSP) | 8889 / 8554 |
| `security-cam` | Flask API + Astro dashboard | 5005 / 3000 |

## Environment configuration

The frontend needs to know where the backend and MediaMTX are. This is configured in `server/.env`:

```ini
PUBLIC_BACKEND_URL=http://<raspberry-pi-ip>:5005
PUBLIC_MEDIAMTX_URL=http://<raspberry-pi-ip>:8889
```

If you access the dashboard through the Access Point, set these to `192.168.4.1`:

```ini
PUBLIC_BACKEND_URL=http://192.168.4.1:5005
PUBLIC_MEDIAMTX_URL=http://192.168.4.1:8889
```

## Troubleshooting

### Dashboard loads but no video feed

- Check MediaMTX is running: `sudo systemctl status mediamtx`
- Verify the stream directly: open `http://<pi-ip>:8889/cam` in a browser
- Check `PUBLIC_MEDIAMTX_URL` in `server/.env` matches the IP you're connecting from

### Cannot reach the dashboard

- Check the Astro server is running: `sudo systemctl status security-cam`
- Make sure you're using port `3000`
- Check firewall: `sudo nft list ruleset`

### API errors in the dashboard

- Check Flask is running: `curl http://localhost:5005/system_info`
- Check `PUBLIC_BACKEND_URL` in `server/.env`

### Service fails on boot

Check the update and start logs:

```bash
journalctl -u security-cam --no-pager -n 30
```

Common causes:
- **No internet** - `git pull` fails. The service continues with the current code, but if this is the first run and deps aren't installed, it will fail. Run `install_requirements.sh` manually once.
- **Build fails** - check Node.js is installed: `node --version`

## Using the dashboard

The web dashboard is the main interface for the security camera system. It's organized into three pages.

### Dashboard (home page)

The main page shows everything at a glance:

- **Live Feed** - real-time camera view via WebRTC, with manual recording controls (start/stop)
- **Sensor Status** - current sensor type, armed/triggered state, and GPIO pin
- **Connection Status** - how many tracked Bluetooth and WiFi devices are online
- **System Health** - CPU temperature, load, RAM usage, and storage
- **Event Timeline** - recent activity: sensor triggers, recording events, device arrivals/departures
- **Health Tracker** - historical system metrics over the last 24-72 hours

### Archive

Browse and manage recorded videos:

- Videos are grouped by date and can be filtered or sorted
- Click a video to stream it directly in the browser
- Delete individual recordings

### Settings

Configure the system without touching config files:

- **Devices** - add or remove tracked Bluetooth and WiFi devices. Scan for nearby devices or enter MAC addresses manually. Tracked devices are used for presence detection - if any are nearby, sensor triggers are ignored.
- **Camera** - adjust resolution, framerate, and rotation. Changes are applied to MediaMTX and take effect after a stream restart.
- **Save Location** - choose where recorded videos are stored on the Pi
- **Appearance** - switch between dark, light, and system theme
- **Trigger Sensors** - select and configure the active sensor type, set the GPIO pin and hold timeout, test wiring with live GPIO readout, and enable/disable auto-recording. See the [trigger sensors guide](./sensors) for supported sensors, wiring, and configuration details.

### How auto-recording works

When a trigger sensor is enabled:

1. The sensor fires (door opens, motion detected, vibration felt, etc.)
2. The system checks if any tracked Bluetooth or WiFi device is nearby
3. If nobody is home, recording starts automatically
4. When the sensor releases, recording continues for the configured hold timeout (default 10 seconds) to prevent gaps from brief interruptions
5. After the hold timeout, recording stops

Manual recording from the dashboard is always allowed, regardless of sensor state or presence detection.
